# 📚 Beginner Level

## Q1. Why does CartWise need a database instead of just storing data in files?

### Answer

Files are simple but fragile. If the backend crashes, in-memory data is lost. If two users access the same file simultaneously, race conditions corrupt it. A database provides:

```text
Persistence     data survives server restarts
Concurrency     multiple users safely
Queries         "get all products in category X" is one query, not code
Transactions    operations succeed or fail together
Constraints     the database prevents bad data (no duplicate slugs, missing prices)
```

CartWise with a database: User A saves an iPhone, User B saves an iPhone on another machine, both persist safely. Without a database, one would overwrite the other.

---

## Q2. What is PostgreSQL, and why did CartWise choose it?

### Answer

PostgreSQL is a relational database — a mature, open-source alternative to MySQL or commercial databases.

CartWise chose it because:
1. It is the target production database (Chapter 23)
2. Using the same database in dev and prod prevents surprises
3. It is stable, well-documented, and standard in web development

The alternative was MySQL (more widely used) or SQLite (simpler), but matching production was the right call.

---

## Q3. What is an @Entity, and how does it relate to a database table?

### Answer

An @Entity is a Java class representing a row type in the database. It maps one-to-one to a table.

```java
@Entity
public class Product { }
       ↓
CREATE TABLE products ( ... );
```

Each field in the entity becomes a column in the table. @Entity classes are how you define your schema in code instead of writing SQL directly.

---

## Q4. What is the difference between `id` and `slug` in the Product entity?

### Answer

`id` is a surrogate key — auto-generated by the database, meaningless to users, purely for internal relationships.

`slug` is a natural key — has business meaning, appears in URLs (`/product/iphone-16-pro`), users can see and understand it.

Both are unique, but `id` is how the database refers to products internally; `slug` is how users refer to them.

---

## Q5. What does `@Column(nullable = false)` do?

### Answer

It creates a `NOT NULL` constraint in the database — the column must always have a value.

```java
@Column(nullable = false)
private String name;
```

Without this, you could insert a product with no name, which would be wrong. The database prevents it.

---

## Q6. What is a foreign key, and why does Wishlist have a `productId` foreign key?

### Answer

A foreign key is a column that references a primary key in another table, creating a relationship.

```java
@Column(nullable = false)
private Long productId;  // foreign key to products.id
```

This means: "this Wishlist item is for a specific Product." The database enforces that the productId must exist in the products table — you cannot save a nonexistent product.

---

## Q7. What is a repository, and what does `JpaRepository<Product, Long>` do?

### Answer

A Repository is a data-access interface. `JpaRepository<Product, Long>` provides automatic CRUD operations:

```text
<Product, Long>
  ↑ entity type
           ↑ primary key type
```

Spring Data JPA generates implementations automatically, so you get `save()`, `findById()`, `findAll()`, `deleteById()` without writing any code.

---

## Q8. How does Spring Data JPA know what `findBySlug(String slug)` should do?

### Answer

It reads the method name and generates SQL:

```
find    → SELECT
By      → WHERE
Slug    → column name slug
```

Becomes: `SELECT * FROM products WHERE slug = ?`

You write the method signature; Spring Data JPA writes the SQL.

---

## Q9. What does `ddl-auto: create-drop` mean, and why is it only for development?

### Answer

`create-drop` tells Hibernate: "on startup, drop all tables and recreate them from @Entity classes."

This is correct for development — you start fresh, test data doesn't accumulate. But in production, it would delete all real user data on every restart.

Production uses `validate` instead — Hibernate checks the schema exists but doesn't change it.

---

## Q10. What is `data.sql`, and when does it run?

### Answer

`data.sql` is a file Spring Boot runs automatically after Hibernate creates the schema, used to seed sample data.

CartWise's `data.sql` inserts 3 sample products on startup, so the database is never empty — Chapter 17 can fetch and return real data.

# 📚 Intermediate Level

## Q11. Explain the full sequence: you start the backend with `mvn spring-boot:run`. Walk through what happens to the database.

### Answer

```text
1. Spring Boot reads application-dev.yml
2. Sees spring.jpa.hibernate.ddl-auto: create-drop
3. Hibernate connects to PostgreSQL
4. Drops all existing tables (products, wishlist, comparison, users)
5. Reads @Entity classes (Product, Wishlist, Comparison, User)
6. Generates CREATE TABLE statements from annotations
7. Executes CREATE TABLE for each entity
8. Spring Boot finds data.sql
9. Runs INSERT statements, seeding 3 sample products
10. Backend is ready, repositories can query data
11. /api/health works, endpoints can use repositories
12. On next startup, entire process repeats — tables dropped, recreated, data reseeded
```

## Q12. Why does Wishlist use plain `Long userId` instead of a relationship annotation like `@ManyToOne`?

### Answer

Because User is not a real entity in Chapter 16 — it is a stub with only `id` and `email`. Adding `@ManyToOne` would require decisions about lazy loading, cascading, and orphan handling — all Chapter 18 concerns.

Using plain `Long` keeps Chapter 16 focused on schema design. Chapter 18 will upgrade it to a proper relationship when User is complete.

## Q13. What does `@Column(unique = true)` on the slug column prevent?

### Answer

It creates a `UNIQUE` constraint — no two rows can have the same slug.

```java
@Column(unique = true)
private String slug;
```

Attempting to insert a second product with slug "iphone-16-pro" will fail with a constraint violation. This protects data integrity.

---

## Q14. Why does Comparison have a `position` field, and what does it enforce?

### Answer

```java
@Column(nullable = false)
private Integer position;  // 0, 1, 2, or 3
```

This tracks the order of items in a Compare selection (first column, second column, etc.). The field itself doesn't enforce a range (0–3), but it is the foundation for the four-item cap:

```text
SELECT * FROM comparison WHERE user_id = ? ORDER BY position
LIMIT 4
```

Only the first 4 rows (positions 0–3) are shown; position 4+ is never allowed.

## Q15. What happens if you try to insert a Wishlist item with a productId that doesn't exist?

### Answer

PostgreSQL rejects it with a foreign key constraint violation:

```text
ERROR: insert or update on table "wishlist" violates 
       foreign key constraint "wishlist_product_id_fkey"
```

The database prevents the insert. This is referential integrity — the database ensures you cannot have a Wishlist item pointing to a nonexistent product.

---

## Q16. Explain the relationship between Product, Wishlist, and User. How many Wishlist rows can reference one Product?

### Answer

```text
One Product → Many Wishlist items
One User → Many Wishlist items
```

Multiple users can save the same product:

```text
Product: iPhone 16 Pro (id=1)
Wishlist rows:
  User A saved it (user_id=1, product_id=1)
  User B saved it (user_id=2, product_id=1)
  User C saved it (user_id=3, product_id=1)
```

Three different Wishlist rows point to the same product — this is normal and correct.

---

## Q17. Why is `createdAt` marked as `updatable = false`?

### Answer

```java
@Column(nullable = false, updatable = false)
private LocalDateTime createdAt;
```

This tells Hibernate: "set this on insert, but never update it."

`createdAt` should be frozen at the moment a row is created and never change. Marking it as `updatable = false` prevents accidental updates and signals the intent to anyone reading the code.

---

## Q18. What is the difference between a natural key and a surrogate key, and why does CartWise have both?

### Answer

```text
Surrogate Key (id)    auto-generated, meaningless, purely for relationships
Natural Key (slug)    has business meaning, appears in URLs
```

Surrogate keys are good for:
- Internal references (Wishlist.productId → Products.id)
- Immutability (id never changes, unlike a name)

Natural keys are good for:
- User-facing identity (URLs, bookmarks)
- Semantic clarity (you know what a slug is)

CartWise uses both: `id` for relationships, `slug` for URLs.

## Q19. What would happen if CartWise used `ddl-auto: create-drop` in production?

### Answer

On the first production restart:

```text
1. Hibernate drops all tables
2. All user data is deleted
3. New empty tables are created
4. Users lose their wishlists and comparisons
5. Disaster
```

This is why production uses `validate` instead — Hibernate checks the schema exists but never modifies it. Schema changes in production go through a migration tool (Chapter 23).

---

## Q20. How does Spring Data JPA generate SQL for a method like `findByUserIdOrderByCreatedAtDesc`?

### Answer

It parses the method name:

```text
find                              → SELECT *
By                                → WHERE
UserId                            → user_id = ?
Order                             → ORDER BY
By                                → (continuation)
CreatedAt                         → created_at
Desc                              → DESC
```

Result: `SELECT * FROM wishlist WHERE user_id = ? ORDER BY created_at DESC`

Spring Data JPA has a vocabulary of keywords (`find`, `By`, `Order`, `Desc`, `And`, `Or`) that it recognizes and translates to SQL.

# ⚛️ JPA/Hibernate-Specific Questions

## Q21. What does `@GeneratedValue(strategy = GenerationType.IDENTITY)` do?

### Answer

It tells Hibernate: "let the database auto-increment the id."

PostgreSQL uses `BIGSERIAL` for this — the sequence increments automatically on each insert.

```text
INSERT INTO products (...) VALUES (...)   (no id provided)
Database auto-generates: id = 1, 2, 3, 4, ...
```

The alternative is `GenerationType.SEQUENCE` (uses a separate sequence object) or `GenerationType.AUTO` (let Hibernate decide).

## Q22. Why is the entity called `Wishlist` (singular) instead of `WishlistItem`?

### Answer

Naming is a judgment call. `Wishlist` is simpler and aligns with the frontend's `useWishlistSelection()` hook returning a list of slugs. `WishlistItem` would be more explicit.

Chapter 16 chose `Wishlist` for conciseness. Either name is correct; consistency is what matters.

---

## Q23. What is the difference between `@Table(name = "products")` and leaving it out?

### Answer

With `@Table`:

```java
@Table(name = "products")
```

Hibernate creates a table named `products`.

Without it, Hibernate defaults to the class name lowercased: `product` (for class `Product`).

Explicitly naming keeps the schema readable and consistent. It is a good practice even when the name would be identical.

---

## Q24. Why are JPA relationships (like `@ManyToOne`) deferred to Chapter 18 instead of added now?

### Answer

Adding `@ManyToOne` requires decisions:

```text
@ManyToOne(fetch = FetchType.LAZY)   vs  @ManyToOne(fetch = FetchType.EAGER)
cascade = CascadeType.REMOVE         vs  cascade = CascadeType.NONE
mappedBy = ...                       deciding on inverse side
```

These are important but outside Chapter 16's scope. Chapter 16 focuses on schema — plain `Long` foreign keys are enough. Chapter 18, when User is complete, will add the annotations and make these decisions.

---

## Q25. What does `Optional<Product> findBySlug(String slug)` return if no product matches?

### Answer

`Optional.empty()` — a Java 8+ way to represent "no value" without null.

```java
repository.findBySlug("nonexistent")
  .ifPresent(p -> System.out.println(p.getName()))
  .orElse(null)   // or handle the empty case
```

Using `Optional` instead of returning `null` is safer and more expressive.

# 🏗️ Database Design Questions

## Q26. Why does the sample data have both `price` and `originalPrice`?

### Answer

`price` is the current price; `originalPrice` is the base price before discounts.

The difference (`originalPrice - price`) is shown as a discount badge on product cards. Without `originalPrice`, you could not show "save ₹10,000" — you would only know the current price.

---

## Q27. The `imageUrl` column stores a string. Why not store the image directly in the database?

### Answer

Storing large binary files (images) in a relational database is inefficient and slow:

```text
Storing URLs instead:
  Small text, easy to query
  Images live on a CDN or file server
  Database stays fast and lean

Storing images directly:
  Database bloats
  Backups become huge
  Queries slow down
```

CartWise stores URLs. Chapter 23 will use a CDN (Cloudinary, S3) for real images; for now, placeholder URLs are fine.

---

## Q28. Why is `reviewCount` stored instead of calculated on-the-fly from a `reviews` table?

### Answer

CartWise doesn't have a `reviews` table yet — that is a future chapter. Storing the count as a denormalized value (one number instead of counting rows) is a performance optimization:

```text
Normalized     COUNT(*) FROM reviews WHERE product_id = 1
Denormalized   SELECT review_count FROM products WHERE id = 1
```

The denormalized version is faster, but it must be kept in sync when reviews are added or deleted. Once reviews are introduced, this trade-off will need revisiting.

---

## Q29. What would a unique constraint on `(user_id, product_id)` in the Wishlist table prevent?

### Answer

```sql
UNIQUE (user_id, product_id)
```

It would prevent the same user from saving the same product twice:

```text
Wishlist rows:
  User 1 saved iPhone (user_id=1, product_id=1)   ✓ allowed
  User 1 saved iPhone again (user_id=1, product_id=1)  ✗ constraint violation
  User 2 saved iPhone (user_id=2, product_id=1)   ✓ allowed
```

This is correct for a wishlist but is deferred to Chapter 18 (after User is a real entity with a foreign key constraint, not a plain `Long`).

---

## Q30. Why is there no `updated_at` column on Wishlist or Comparison, only `created_at`?

### Answer

Wishlist items are write-once: you save a product, it stays saved with that creation timestamp. There is no "update" operation — you remove it or keep it.

If an "update" operation were added (e.g., re-save an already-saved product), then `updated_at` would make sense. For now, only `created_at` is needed.

# 🧪 Scenario-Based Questions

## Q31. A user saved an iPhone on Monday and a Galaxy on Tuesday. How would you query the Wishlist to show them in reverse chronological order (newest first)?

### Answer

```sql
SELECT * FROM wishlist 
WHERE user_id = ?
ORDER BY created_at DESC;
```

Or in the repository:

```java
List<Wishlist> findByUserIdOrderByCreatedAtDesc(Long userId);
```

The `created_at` timestamp and `DESC` order make this trivial — it is the exact method in `WishlistRepository`.

---

## Q32. A product's price drops from ₹129,999 to ₹99,999. How do you update the database, and what rows need to change?

### Answer

```sql
UPDATE products 
SET price = 99999, updated_at = NOW()
WHERE id = 1;
```

Only the `products` row changes. All Wishlist items referencing this product (`wishlist.product_id = 1`) automatically see the new price when they query:

```sql
SELECT p.price 
FROM wishlist w
JOIN products p ON w.product_id = p.id
WHERE w.user_id = 1 AND w.product_id = 1;
```

This is why storing only the productId, not a copy of the price, is the right design — the price updates once, and every reference sees it.

---

## Q33. A product is removed from the catalogue (delisted). What happens to Wishlist items that saved it?

### Answer

Currently (Chapter 16), nothing automatic happens. The `productId` foreign key constraint prevents the product row from being deleted if any Wishlist items reference it — so the product cannot be delisted without first removing it from all wishlists.

This is the safe default. Chapter 18+ might add `ON DELETE CASCADE` to automatically remove Wishlist items when a product is deleted, or `ON DELETE SET NULL` to orphan them. The decision depends on business logic Chapter 16 doesn't define.

---

## Q34. You query `SELECT * FROM products ORDER BY rating DESC` and get two products both rated 4.8. The order between them is arbitrary. How would you fix this?

### Answer

Add a tiebreaker — usually `review_count`:

```sql
SELECT * FROM products 
ORDER BY rating DESC, review_count DESC;
```

A 4.8 rating from 12,000 reviews is more meaningful than 4.8 from 10 reviews. The tiebreaker makes results consistent and user-friendly.

The frontend already does this (Chapter 13), and it should be done at the database query level too.

---

## Q35. The backend logs show `Hibernate: create table wishlist (id bigserial...)` but when you query PostgreSQL directly, the table doesn't exist. What happened?

### Answer

Two possibilities:

1. **Connected to the wrong database.** You ran the backend against `cartwise_dev`, but you are querying a different database (the default `postgres` database, or a `test_cartwise` database). Check the connection string in the logs.

2. **The backend crashed before finishing startup.** The CREATE TABLE statements were logged but never executed. Check the full startup log for error messages after the DDL statements.

Run `\l` in psql to list all databases and confirm you are in the right one.
